# 무더위쉼터 OpenAPI 활용 및 팀 협업 가이드

> 구현 상태(2026-08-11): 재난안전데이터공유플랫폼 `DSSP-IF-10942` 연동이 완료됐다. 현재 코드는 `src/data/safety_shelters.py`에서 좌표 범위 페이지네이션, 대구 주소 재필터링, 표준 스키마 변환과 마지막 정상 캐시를 처리한다. 아래 내용 중 공공데이터포털 승인 대기 관련 설명은 초기 설계 기록으로 보존한다.

작성일: 2026-08-11  
대상 API: 행정안전부_무더위쉼터 (공공데이터포털 데이터 ID `15138456`)

## 1. 결론

무더위쉼터는 공공데이터포털 OpenAPI를 운영 데이터의 원본으로 사용한다. 현재 `data` 폴더의 CSV는 버리지 않고 API 장애, 응답 변경, 발표 당일 네트워크 문제에 대비한 **검증·Fallback 스냅샷**으로 사용한다.

프론트엔드에서 공공데이터 API를 직접 호출하지 않는다. 개발팀이 서버 측에서 API 키를 사용해 데이터를 수집·정규화하고, 데이터팀의 분석 코드와 프론트엔드는 동일한 내부 데이터 규격을 사용한다.

```text
공공데이터포털 OpenAPI
        ↓
개발팀 API 클라이언트 · 캐시
        ↓
공통 무더위쉼터 표준 스키마
        ├─ 데이터팀: 접근성·서비스권·사각지대 분석
        └─ 프론트엔드: 지도 마커·필터·상세 패널
```

## 2. 공식 API 확인 결과

- OpenAPI 명: `행정안전부_무더위쉼터`
- 제공기관: 행정안전부 기후재난대응과
- 제공 형식: JSON, XML
- 주요 제공 내용: 쉼터시설번호, 연도, 지역코드, 시설구분, 쉼터명칭, 상세주소, 면적, 이용가능인원, 선풍기·에어컨 보유 수 등
- 비용: 무료
- 이용허락범위: 제한 없음
- 개발계정: 자동승인
- 운영계정: 심의승인
- 트래픽 한도: 포털에 고정 수치가 공개되어 있지 않으며 기관 정책에 따라 달라질 수 있음

주의할 점은 예전 `HeatWaveShelter`, `HeatWaveShelter2`, `HeatWaveShelter3` API가 아니라 데이터 ID `15138456`의 **신규 대체 API**를 신청해야 한다는 것이다. 공공데이터포털은 기존 서비스의 제공중단 예정일을 2025-01-15 이후로 안내했다.

정확한 요청 URL과 요청 파라미터는 활용신청 완료 후 공공데이터포털의 `마이페이지 → OpenAPI → 개발계정 상세보기`에 표시되는 명세를 기준으로 확정한다. 현재 공개 페이지는 API 유형을 `LINK`로 표시하며 비로그인 상태에서는 실제 요청 URL을 노출하지 않으므로, 구형 URL을 추측해서 코드에 넣으면 안 된다.

공식 자료:

- https://www.data.go.kr/data/15138456/openapi.do
- https://www.data.go.kr/bbs/ntc/selectNotice.do?originId=NOTICE_0000000003809

## 3. 최초 준비 담당

팀에서 공공데이터포털 **프로젝트 서비스키 하나**를 발급하고 배포용 키로 사용한다. 개인 서비스키는 각자 로컬 테스트에만 사용한다.

활용신청 담당자가 팀에 전달할 것은 다음 세 가지다.

1. 신규 API의 실제 요청 URL
2. 개발계정 상세보기의 요청·응답 명세 또는 스크린샷
3. 키를 제거한 성공 응답 JSON 1건

서비스키 자체는 메신저, 문서, GitHub Issue 또는 소스 코드로 공유하지 않는다. Streamlit Cloud에서는 앱의 `Settings → Secrets`, 로컬에서는 `.env`에 각자 넣는다.

```dotenv
SAFETY_DATA_SHELTER_API_URL=https://www.safetydata.go.kr/V2/api/DSSP-IF-10942
SAFETY_DATA_SERVICE_KEY=발급받은키
API_TIMEOUT_SECONDS=10
```

Streamlit Cloud TOML:

```toml
SAFETY_DATA_SHELTER_API_URL = "https://www.safetydata.go.kr/V2/api/DSSP-IF-10942"
SAFETY_DATA_SERVICE_KEY = "발급받은키"
API_TIMEOUT_SECONDS = "10"
```

공공데이터포털에서 일반키와 URL 인코딩키를 함께 보여주는 경우가 있다. Python `requests.get(..., params=...)`에 키를 넣으면 라이브러리가 인코딩하므로 키가 이중 인코딩되지 않았는지 실제 성공 요청으로 확인한다.

## 4. 개발팀 담당 범위

### 4.1 API 클라이언트

`src/shelter_client.py`를 만들고 다음 책임만 둔다.

- 환경변수와 Streamlit Secrets에서 요청 URL·서비스키 읽기
- 페이지네이션으로 전체 데이터 수집
- JSON 우선 요청, 필요할 때 XML 응답 처리
- timeout, HTTP 오류, 공공데이터 오류 코드 처리
- 원본 응답 컬럼을 변경하지 않고 반환
- API 키와 키가 포함된 요청 URL을 로그에 남기지 않기

요청 파라미터 이름은 활용신청 명세에서 확인한 값을 사용한다. 일반적으로 서비스키, 페이지 번호, 페이지당 건수, 응답 형식이 필요하지만, 이 API의 실제 명세와 다른 이름을 임의로 가정하지 않는다.

### 4.2 정규화 계층

`src/shelter_repository.py`에서 API의 한글 원본 컬럼을 다음 내부 스키마로 변환한다.

```python
{
    "shelter_id": "시설 고유번호",
    "name": "무더위쉼터명",
    "facility_type": "경로당",
    "address": "대구광역시 ...",
    "region_code": "공식 지역코드",
    "data_year": 2025,
    "area_m2": 25.0,
    "capacity": 7,
    "fan_count": 4,
    "air_conditioner_count": 2,
    "latitude": 35.8538526,
    "longitude": 128.6275303,
    "status": "운영",
    "source": "행정안전부_무더위쉼터",
    "fetched_at": "2026-08-11T15:00:00+09:00"
}
```

원본 응답에 위도·경도가 없거나 비정상인 시설은 별도로 분리한다. 주소 지오코딩이 필요하면 원본 좌표와 지오코딩 좌표를 구분하고, 데이터팀이 좌표 생성 방법과 정확도를 기록한다. 지도에 전달하는 최종 좌표계는 WGS84, EPSG:4326으로 통일한다.

### 4.3 캐시와 장애 대응

- 앱 화면을 다시 그릴 때마다 공공 API를 호출하지 않는다.
- 서버 메모리 캐시는 6시간을 기본값으로 사용한다.
- 정상 응답은 로컬 스냅샷으로 보존할 수 있게 한다.
- API 실패 시 마지막 정상 스냅샷, 그다음 현재 `data` 폴더 CSV 순으로 대체한다.
- Fallback 사용 시 화면에 `데이터 갱신 시각`과 `API 장애로 저장본 사용 중`을 표시한다.
- 빈 응답은 정상 데이터로 캐시하지 않는다.

### 4.4 프론트엔드 연결

프론트엔드는 정규화된 목록만 받아 다음 기능을 구현한다.

- SGIS 행정동 경계 위에 쉼터를 점 또는 아이콘으로 표시
- 시설 유형, 주말·야간 운영, 수용인원으로 필터링
- 시설 클릭 시 명칭, 주소, 유형, 수용인원, 냉방시설 정보 표시
- 선택한 행정동의 시설만 강조하고 개수·총수용인원 집계
- API 출처와 기준연도·최종 갱신시각 표시

쉼터 좌표는 **시설 점 레이어**다. 취약도 Heat Map은 데이터팀이 산출한 행정동 또는 격자별 취약도 값으로 별도 표현하고, 두 레이어를 겹쳐 사각지대를 보여준다.

현재 UI 계약과 연결할 때는 최소한 다음 형태로 변환한다.

```python
{
    "name": shelter["name"],
    "type": shelter["facility_type"],
    "latitude": shelter["latitude"],
    "longitude": shelter["longitude"],
    "status": shelter["status"],
}
```

## 5. 데이터팀 담당 범위

데이터팀은 공공 API 호출 코드를 여러 분석 노트북에 복사하지 않는다. 개발팀의 정규화 함수 또는 정규화된 Parquet/CSV 스냅샷을 입력으로 사용한다.

### 5.1 품질검사

- 시설 고유번호 중복 검사
- 위도·경도 결측 및 대구 범위 이탈 검사
- 폐쇄·삭제·미운영 시설 제외 기준 정의
- 수용인원, 면적, 냉방기 수의 숫자 변환과 이상치 검사
- 같은 주소 또는 좌표를 공유하는 복합시설의 중복 여부 확인
- 시설 유형 표준화
- API 데이터의 기준연도와 수집 시각 기록

### 5.2 분석용 산출물

데이터팀은 `adm_cd`별로 다음 결과를 만들어 개발팀에 전달한다.

```python
{
    "adm_cd": "행정동 코드",
    "shelter_count": 12,
    "total_capacity": 430,
    "nearest_shelter_distance_m": 820,
    "accessible_population": 720,
    "underserved_population": 710,
    "coverage_rate": 50.3,
    "blind_spot": True,
    "blind_spot_count": 4,
    "existing_facilities": [],
    "service_areas_geojson": {},
    "blind_spot_geojson": {},
    "analysis_standard": {
        "distance_m": 500,
        "distance_type": "walking_or_euclidean",
        "capacity_considered": True
    }
}
```

`existing_facilities`에는 개발팀의 표준 쉼터 객체를 그대로 넣는다. 이렇게 하면 분석 결과와 지도 마커가 서로 다른 시설 목록을 사용하는 문제를 막을 수 있다.

### 5.3 사각지대 산정 시 합의할 기준

- 접근 기준: 도보 5분, 10분 또는 거리 300m, 500m 중 무엇을 사용할지
- 거리 방식: 직선거리인지 도로망 기반 보행거리인지
- 시설 수용량을 초과한 인구를 미충족 인구로 볼지
- 주말·야간 미운영 시설을 해당 시간대 분석에서 제외할지
- 행정동 경계 밖 시설도 경계 인근 주민이 이용할 수 있게 포함할지
- 취약인구를 행정동 총량으로 볼지 격자·집계구로 배분할지

해커톤 시간 안에는 1차로 `500m 직선거리 + 수용량 반영`을 기준으로 구현하고, 화면과 결과의 `analysis_standard`에 한계를 명시하는 방식을 권장한다.

## 6. 팀 간 파일·함수 계약

| 전달 주체 | 전달 대상 | 전달물 | 기본키 |
|---|---|---|---|
| 개발팀 | 데이터팀 | 정규화된 전체 쉼터 목록 | `shelter_id` |
| 데이터팀 | 개발팀 | 행정동별 접근성·사각지대 결과 | `adm_cd` |
| 개발팀 | 프론트엔드 | 지도용 쉼터 목록과 상세정보 | `shelter_id` |
| 데이터팀 | 프론트엔드 | Heat Map 점수·서비스권·사각지대 GeoJSON | `adm_cd` |
| SGIS 클라이언트 | 전체 | 행정동 경계와 행정동 코드 | `adm_cd` |

행정동명은 표기 방식이 달라질 수 있으므로 조인 키로 사용하지 않는다. SGIS 경계, 취약도, 접근성 결과는 모두 `adm_cd`를 기준으로 결합한다.
