# 현재 개발 상태 및 팀 협업·통합 계획

작성일: 2026-08-11  
대상 프로젝트: 폭염 취약지역·대응시설 사각지대 분석 및 정책 우선순위 추천 서비스

## 1. 한 줄 결론

현재 결과물은 **고정된 Mock 데이터를 사용해 서비스의 전체 사용자 흐름을 시연할 수 있도록 만든 UI 중심 MVP**다.

단순한 정적 페이지와 완전히 같지는 않다. 사용자가 입력한 예산과 설치 가능 시설 수에 따라 후보 시설 선택, 총비용, 추가 접근 가능 인구, 서비스권 비율, 접근 취약인구와 사각지대 수가 다시 계산된다. 또한 입력 검증, 모듈별 오류 격리, 정책 JSON 검증 같은 통합 기반도 구현되어 있다.

그러나 핵심 분석에 필요한 실제 공공데이터, 학습 모델, GIS 분석, 최적화 모델 및 Alan API가 아직 연결되지 않았으므로 **현재 화면에 나타나는 점수·인구·위치·시설·정책 내용은 정책 판단에 사용할 수 없는 시연용 값**이다. 실데이터 모드를 선택하더라도 현재는 실제 분석 provider가 없어서 각 단계가 Mock 결과로 대체된다.

## 2. 현재 구현된 범위

| 구분 | 현재 상태 | 실제 동작 여부 | 비고 |
|---|---|---:|---|
| Streamlit 화면 | 구현 완료 | O | 기본/다크 모드와 데스크톱·모바일 반응형 지원 |
| 지도 기반 지역 선택 | 부분 실데이터 | O | SGIS 2025 대구 행정동 실제 경계를 사용하며 분석값이 있는 3개 동을 클릭 가능 |
| 예산·시설 수 입력 | 구현 완료 | O | 0 이상 정수 검증 |
| 폭염 취약도 | Mock 구현 | 제한적 | 지역별 점수·등급·원인이 코드에 고정됨 |
| 시설 접근성 | Mock 구현 | 제한적 | 시설 위치·거리·인구·사각지대가 코드에 고정됨 |
| 입지 추천 | 간이 로직 구현 | O | 고정 후보 중 `추가 접근인구 / 비용` 순으로 선택 |
| Before/After | 간이 계산 구현 | O | 선택된 후보의 추가 접근인구를 합산해 재계산 |
| 지도 | 부분 실데이터 | O | SGIS 실제 경계 150개 표시. 취약도 색상은 3개 동의 Mock 값이며 나머지는 미분석 표시 |
| 정책 추천 | Mock 구현 | 제한적 | 분석 결과를 조합한 고정 템플릿 정책 |
| Alan API | 연결 경계만 구현 | X | 공식 요청 명세가 없어 실제 호출 직전에 중단하고 Mock으로 대체 |
| 장애 복구 | 구현 완료 | O | 개별 분석 실패 시 경고를 남기고 Mock으로 대체 |
| 자동 테스트 | 기본 구현 | O | 입력, 예산, 시설 수, 정책 스키마, 후보지 제한, 키 노출 여부 검사 |

## 3. 현재 하드코딩된 부분

### 3.1 지역 및 기초 데이터

`src/mock_data.py`에 다음 정보가 직접 작성되어 있다.

- 지원 행정동 3곳
- 행정동 중심 좌표
- SGIS 장애 시 사용하는 지도 선택용 간이 폴리곤
- 폭염 취약도 점수와 등급
- 취약인구 수와 주요 취약 원인
- 시설 접근성 점수와 가장 가까운 쉼터 거리
- 접근 가능·접근 취약 인구
- 기존 시설 명칭, 유형, 위도·경도, 운영 상태
- 신규 시설 후보 명칭, 유형, 좌표, 비용, 추가 보호 인구와 선정 근거

이 값은 데이터 파일이나 데이터베이스에서 읽은 것이 아니며, 최신 공공데이터와 연결되어 있지 않다.

### 3.2 폭염 취약도 분석

`src/vulnerability.py`는 실제 모델을 실행하지 않는다. 팀원이 만든 함수를 `provider(region) -> dict` 형태로 연결할 수 있는 어댑터와 필수 필드 검증만 있다.

현재 빠져 있는 핵심 기능은 다음과 같다.

- 기온, 습도, 열지수, 폭염일수 등 기상 데이터 수집·전처리
- LST, NDVI, 녹지율 등 환경 데이터 결합
- 고령인구, 독거노인, 기초생활수급자 등 취약인구 데이터 결합
- 행정동/격자 단위 공간 정합성 처리
- XGBoost·LightGBM 또는 가중치 기반 취약도 산출
- SHAP 또는 대체 설명 기법을 이용한 주요 취약 원인 산출
- 점수 정규화와 위험등급 기준 정의 및 검증

### 3.3 시설 접근성 및 사각지대 분석

`src/accessibility.py`에도 실제 공간 분석은 없고 provider 연결 규격만 있다.

현재 빠져 있는 핵심 기능은 다음과 같다.

- 실제 무더위쉼터 위치·운영시간·수용인원 데이터
- 취약인구 분포와 시설 서비스권의 공간 결합
- 직선거리 대신 보행 네트워크 기반 접근거리 계산
- 기준 거리 안에 포함되는 접근 가능 인구 산출
- 시설 수용능력을 고려한 공급 부족 판단
- 사각지대의 위치, 면적, 취약인구 및 개수 산출
- 폐쇄·미운영·계절 운영 시설 처리

### 3.4 입지 추천과 What-if 분석

현재 입지 추천은 미리 정의된 후보를 비용 효율 순으로 정렬한 뒤 예산과 시설 수 범위에서 앞에서부터 선택하는 휴리스틱이다.

아직 반영되지 않은 요소는 다음과 같다.

- 설치 가능한 실제 후보지 생성 및 설치 불가 지역 제외
- 후보 간 서비스권 중복 제거
- 시설 유형별 비용·수용량·운영비 차이
- 최대 커버리지, p-median 등 입지 최적화 모델
- 예산·시설 수·형평성·행정구역별 최소 배치 같은 복수 제약
- 실제 보행거리와 추가 접근 가능 인구 재계산
- 여러 정책 시나리오 비교 및 민감도 분석

### 3.5 Alan 정책 추천

`src/alan_client.py`에는 다음 기반이 구현되어 있다.

- 환경변수 또는 Streamlit secrets에서 키 읽기
- Alan에 전달할 사실 데이터의 범위 제한
- 입력에 없는 위치·비용·통계 생성 금지 프롬프트
- 정책 JSON 스키마 검증
- 추천 후보지 외 위치 사용 금지
- 최대 3개 정책 제한
- timeout, HTTP 오류, JSON 파싱 오류 처리 경계
- API 오류 시 Mock 정책 반환

그러나 Alan 공식 API의 엔드포인트, 인증 방식, 요청 필드 및 응답 구조가 확인되지 않았기 때문에 `_build_request_payload()`는 의도적으로 구현되지 않았다. 현재는 키와 URL을 입력해도 실제 Alan 호출이 완료되지 않는다.

## 4. 현재 코드에서 재사용할 수 있는 부분

실제 데이터와 모델을 연결할 때 전체 화면을 다시 만들 필요는 없다. 다음 부분은 유지할 수 있다.

- `app.py`의 입력·결과 화면과 기본/다크/반응형 UI
- 지도 영역 클릭을 통한 지역 선택 흐름
- `run_policy_analysis()` 단일 통합 진입점
- 취약도 → 접근성 → 최적화 → 정책 추천 실행 순서
- 각 분석 모듈의 표준 출력 스키마
- 모듈별 예외 처리와 `warnings` 수집
- 예산 및 시설 수 검증
- Alan 프롬프트의 환각 방지 규칙과 응답 검증
- Mock/실데이터 모드 분리
- 기존 자동 테스트 구조

즉, 다른 팀은 화면 코드를 직접 수정하기보다 **정해진 함수와 출력 스키마를 구현해 어댑터 뒤에 연결하는 방식**으로 협업하는 것이 안전하다.

## 5. 팀별 협업 대상과 전달받아야 할 결과

### 5.1 데이터 수집·전처리 팀

담당 범위:

- 기상청, 통계청·KOSIS, 행정안전부, 환경·위성 데이터 확보
- 행정동 코드와 기준연도 통일
- 좌표계 통일 및 결측치·이상치 처리
- 원천 데이터와 가공 데이터 분리
- 데이터 출처, 기준일, 라이선스와 갱신 주기 기록

통합 팀에 전달할 것:

- 행정동별 분석 테이블(CSV 또는 Parquet)
- 행정동 경계 GeoJSON
- 기존 무더위쉼터 데이터
- 취약인구의 행정동 또는 격자 단위 데이터
- 데이터 사전: 컬럼명, 단위, 기준연도, 결측 처리 방식
- 재생성 가능한 전처리 스크립트

합의해야 할 사항:

- 지역 식별자는 화면 이름이 아니라 공식 행정동 코드를 기본키로 사용
- 인구·기상·환경 데이터의 기준연도 차이를 어떻게 표시할지 결정
- 위도·경도는 WGS84(EPSG:4326)로 화면에 전달

### 5.2 폭염 취약도 모델 팀

담당 범위:

- 취약도 계산 또는 예측 모델 구현
- 점수의 0~100 정규화 방식과 등급 경계 정의
- 주요 위험 원인의 값과 기여도 산출
- 학습·검증 지표와 모델 한계 문서화

통합 함수 계약:

```python
def analyze_vulnerability(region: str) -> dict:
    return {
        "region": "대구광역시 달서구 송현1동",
        "vulnerability_score": 87.2,
        "vulnerability_grade": "위험",
        "main_causes": [
            {"name": "고령인구 비율", "value": 31.2, "contribution": 0.34}
        ],
        "vulnerable_population": 1430,
    }
```

필수 협의:

- `contribution`은 0~1 값으로 전달
- 점수와 등급은 같은 기준표를 사용
- 모델 파일 경로를 코드에 고정하지 않고 설정 또는 로더로 분리
- 모델 미학습·데이터 누락 시 이해 가능한 예외를 발생시킴

### 5.3 GIS·시설 접근성 팀

담당 범위:

- 기존 시설과 취약인구의 공간 분석
- 접근 기준 거리 또는 보행 시간 정의
- 시설별 서비스권 및 수용능력 계산
- 사각지대 GeoJSON 또는 좌표 목록 생성

통합 함수 계약:

```python
def analyze_accessibility(region: str) -> dict:
    return {
        "facility_score": 32.5,
        "nearest_shelter_distance_m": 820,
        "accessible_population": 720,
        "underserved_population": 710,
        "coverage_rate": 50.3,
        "blind_spot": True,
        "blind_spot_count": 4,
        "existing_facilities": [
            {
                "name": "시설명",
                "type": "무더위쉼터",
                "latitude": 35.0,
                "longitude": 128.0,
                "status": "운영",
            }
        ],
        "map_center": {"latitude": 35.0, "longitude": 128.0},
    }
```

추가 권장 필드:

- `blind_spot_geojson`: 사각지대 폴리곤
- `service_areas_geojson`: 기존 시설 서비스권
- `average_walking_distance_m`: 평균 보행거리
- `analysis_standard`: 접근 기준 거리와 산정 방식

새 필드는 기존 필드를 제거하지 않고 추가해야 화면과 테스트의 하위 호환성을 유지할 수 있다.

### 5.4 입지 최적화 팀

담당 범위:

- 설치 가능 후보지 목록 생성
- 예산과 최대 시설 수를 만족하는 조합 탐색
- 후보 간 중복 커버리지를 고려한 추가 보호 인구 계산
- 설치 전후 접근성과 사각지대 재계산

통합 함수 계약:

```python
def recommend_locations(
    region: str,
    budget: int,
    max_facilities: int,
    vulnerability: dict,
    accessibility: dict,
) -> dict:
    return {
        "budget": budget,
        "max_facilities": max_facilities,
        "total_estimated_cost": 20_000_000,
        "recommended_locations": [
            {
                "name": "후보지명",
                "latitude": 35.0,
                "longitude": 128.0,
                "facility_type": "그늘막",
                "estimated_cost": 20_000_000,
                "additional_covered_population": 430,
                "reason": "계산된 선정 근거",
            }
        ],
        "before": {
            "coverage_rate": 50.3,
            "underserved_population": 710,
            "blind_spot_count": 4,
        },
        "after": {
            "coverage_rate": 80.4,
            "underserved_population": 280,
            "blind_spot_count": 2,
        },
    }
```

반드시 만족해야 할 조건:

- 추천 비용 합계가 입력 예산을 초과하지 않음
- 추천 시설 수가 `max_facilities`를 초과하지 않음
- 추천 위치는 입력 후보지에 실제로 존재함
- 설치 후 접근 취약인구와 사각지대가 음수가 되지 않음
- 동일 인구를 여러 시설의 효과로 중복 계산하지 않음

### 5.5 Alan/API·정책 팀

담당 범위:

- Alan 공식 API 문서와 실제 호출 예제 확보
- 공식 인증·요청·응답 구조 확인
- 정책 후보 목록과 행정 용어 검토
- 실패·timeout·호출 한도에 대한 운영 기준 정의

통합 팀에 전달할 것:

- 공식 API 문서 링크 또는 사본
- 최소 동작 요청/응답 예제(키 제거)
- 모델이 반환하는 JSON의 실제 위치
- rate limit, timeout 권장값, 오류 코드
- Mock과 실응답의 필드 대응표

통합 시 작업:

- `AlanPolicyClient._build_request_payload()` 구현
- 실제 응답에서 정책 JSON을 추출하는 별도 메서드 구현
- 응답 원문은 내부 진단용으로만 보관하고 화면에는 검증된 필드만 전달
- 실패 시 Mock을 쓸지, 정책 추천만 실패 상태로 표시할지 운영 정책 결정

### 5.6 통합·UI 팀

담당 범위:

- 각 팀 함수의 어댑터 연결
- 스키마 검증과 사용자 오류 메시지 유지
- 지도에 행정동 경계, Heat Map, 서비스권과 사각지대 레이어 추가
- 데이터 기준일·출처·분석 기준을 화면에 표시
- 모바일/다크 모드와 발표 시나리오 유지
- 통합 테스트와 시연 데이터 백업 유지

다른 팀 코드 병합 원칙:

- 팀원이 만든 모델 파일을 `app.py`에서 직접 호출하지 않음
- 각 모듈 내부에서 실제 구현을 호출하고 표준 딕셔너리로 변환
- 팀 모델의 원래 함수명이나 출력이 다르면 재작성하지 않고 어댑터에서 변환
- 실데이터 실패 시 원인을 `warnings`에 남기되 API 키나 원천 응답 전체를 노출하지 않음
- Mock 모드는 마지막까지 유지해 시연 실패에 대비

## 6. 권장 통합 순서

### 1단계: 데이터 계약 확정

1. 공식 행정동 코드와 분석 단위를 결정한다.
2. 팀별 입력·출력 예제 JSON을 저장소에 공유한다.
3. 단위, 좌표계, 기준연도와 결측 처리 규칙을 합의한다.
4. 실제 파일을 합치기 전에 예제 데이터로 계약 테스트를 만든다.

### 2단계: 실제 분석 모듈 연결

1. 취약도 provider를 연결하고 Mock 결과와 필드를 비교한다.
2. 접근성 provider를 연결하고 인구 합계와 거리 단위를 검증한다.
3. 최적화 provider를 연결하고 예산·시설 수·중복 커버리지 조건을 검사한다.
4. 각 모듈을 단독 테스트한 뒤 `run_policy_analysis()`에서 통합한다.

### 3단계: 공간 시각화 확장

1. 행정동 경계와 취약도 Heat Map을 추가한다.
2. 기존 시설 서비스권과 사각지대 폴리곤을 추가한다.
3. 신규 후보 선택 전후의 지도 레이어를 전환할 수 있게 한다.
4. 범례, 단위, 기준일과 데이터 출처를 표시한다.

### 4단계: Alan 연결

1. 공식 명세로 요청 payload를 구현한다.
2. 실응답에서 JSON을 추출하고 현재 validator를 통과시키도록 한다.
3. 입력 후보 이외 위치가 나오면 응답을 거부하고 사용자에게 알린다.
4. timeout과 오류 상황을 재현해 전체 앱이 계속 동작하는지 확인한다.

### 5단계: 최종 시연·배포 검증

1. 실데이터 모드와 Mock 모드를 각각 처음부터 끝까지 실행한다.
2. 발표용 대표 지역과 입력값을 고정한다.
3. 네트워크/API 장애 시 Mock 전환 절차를 확인한다.
4. 데스크톱, 태블릿, 모바일 및 기본/다크 모드를 확인한다.
5. 개인정보, API 키, 절대경로와 디버그 로그가 노출되지 않는지 검사한다.

## 7. 우선순위별 보완 과제

### P0: 시연 전에 반드시 필요

- 실제 데이터의 최소 1개 행정동 연결
- 취약도 또는 접근성 중 팀의 핵심 분석 결과 최소 1개 실제 연결
- 입지 추천 입력 후보와 비용의 출처 명시
- 실데이터/Mock 여부를 결과 화면에서 명확히 구분
- 데이터 기준일과 분석 한계 표시
- 전체 통합 테스트 및 장애 시 Mock 전환 확인

### P1: 해커톤 완성도를 크게 높이는 항목

- 행정동 취약도 Heat Map
- 시설 서비스권과 사각지대 폴리곤
- 후보 간 중복 커버리지를 고려한 최적화
- Alan 실제 API 연결 및 응답 스키마 검증
- 데이터 출처와 모델 설명을 화면에서 조회

### P2: 후속 고도화

- 실시간 기상·예보 데이터 반영
- 시설 운영시간·수용량과 보행 네트워크 반영
- 여러 예산 시나리오 저장·비교
- 모델 성능·편향 모니터링
- 분석 결과 다운로드 및 정책 보고서 자동 생성
- 인증, 사용자 권한, 데이터베이스 및 배포 모니터링

## 8. 통합 완료 판단 기준

다음 조건을 만족하면 “하드코딩된 시연 페이지”에서 “데이터 기반 정책지원 MVP”로 넘어갔다고 판단할 수 있다.

- 화면에 표시되는 지역·점수·인구·시설·후보지가 실제 데이터에서 생성됨
- 취약도 점수와 위험 원인의 산출 근거가 재현 가능함
- 시설 접근성과 사각지대가 공간 분석 결과로 생성됨
- 추천 후보가 실제 설치 가능 후보 목록과 예산 제약을 만족함
- Before/After 값이 최적화 결과를 이용해 재계산됨
- Alan 정책이 검증된 분석 결과와 후보지만 사용함
- 각 데이터의 출처, 기준일, 단위와 분석 한계가 표시됨
- 모듈 하나 또는 API가 실패해도 서비스 전체가 종료되지 않음
- 실제 모드에 대한 자동 테스트와 최소 1개 기준 시나리오가 통과함

## 9. 현재 상태에서의 시연 표현 가이드

현재 버전을 발표할 때는 다음과 같이 설명하는 것이 정확하다.

> 현재 버전은 전체 정책 의사결정 흐름과 통합 인터페이스를 검증하기 위한 Mock 기반 MVP입니다. 예산과 시설 수에 따른 추천 및 Before/After 계산은 동작하지만, 표시되는 기초 수치와 후보지는 시연 데이터입니다. 각 분석 팀의 모델과 공공데이터는 표준 함수 계약을 통해 교체·연결하도록 준비되어 있습니다.

피해야 할 표현:

- “AI가 실제 대구 폭염 위험을 예측했다.”
- “추천 위치가 실제 최적 입지다.”
- “이 시설을 설치하면 온열질환이 일정 비율 감소한다.”
- “Alan API가 현재 실제 정책을 생성하고 있다.”

이러한 표현은 실제 데이터·모델·API 연결과 검증이 완료된 뒤에만 사용해야 한다.
